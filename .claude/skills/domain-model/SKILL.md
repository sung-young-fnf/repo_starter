# /domain-model — 도메인 모델링 세션

**코드를 쓰기 전, 계획을 세우기도 전** 단계다. 여기서 나온 문서가 이후 모든 이름의 근거가 된다.

## 언제 쓰나

- 새 서비스/새 도메인을 시작할 때
- 기획서를 받았는데 **같은 단어가 서로 다른 뜻으로 쓰이는** 것 같을 때
- 기존 모델에 새 개념을 우겨넣기 어려울 때 (경계가 잘못 그어졌다는 신호)
- 팀에서 같은 것을 다른 이름으로 부르고 있을 때

CRUD 화면 하나 추가하는 정도라면 **이 스킬은 필요 없다.** 바로 `/ddd-plan` 으로 간다.

---

## Phase 1. 입력 확보

사용자에게 다음이 없으면 요청한다.

- 요구사항/기획서 (문서, 링크, 혹은 구두 설명)
- 이 기능이 **누구의 어떤 문제**를 푸는지
- 기존 시스템이 있다면 지금 어떻게 처리하는지

기존 코드가 있으면 `src/contexts/` 또는 `app/contexts/`, `docs/domain/` 을 읽어
**이미 존재하는 용어와 경계**를 확보한다. 있는 개념에 새 이름을 붙이지 않기 위해서다.

---

## Phase 2. 이벤트스토밍

`domain-modeler` 에이전트를 호출한다. 요구사항 원문과 기존 컨텍스트 요약을 전달한다.

에이전트는 **명사가 아니라 사건부터** 시작한다.

```
1. 도메인 이벤트     "예약이 확정되었다"  (과거형)
2. 커맨드            "예약을 확정한다"
3. 애그리거트        이벤트/커맨드를 묶는 일관성 단위
4. 정책              "확정되면 알림을 보낸다"  (이벤트 → 커맨드)
5. 읽기 모델         화면이 필요로 하는 조회 형태
6. 바운디드 컨텍스트  언어가 갈리는 지점에 선 긋기
```

---

## Phase 3. 검증 — 사용자와 함께

에이전트 결과를 받아 **사용자에게 확인할 것을 골라 묻는다.** 추측으로 채우지 않는다.

특히 다음은 반드시 사람에게 확인한다.

- **같은 단어의 다른 뜻**: "정산에서 말하는 '고객'과 예약에서 말하는 '고객'이 같은 대상인가요?"
- **불변식의 강도**: "정원 초과는 절대 안 되나요, 아니면 잠깐 초과됐다가 조정돼도 되나요?"
  → 이 답이 트랜잭션 경계를 결정한다.
- **상태 전이의 예외**: "관리자는 취소된 예약을 되살릴 수 있나요?"
- **누가 소유하는가**: "이 데이터의 원본은 우리 시스템인가요, 외부 시스템인가요?"
  → 외부면 ACL 이 필요하다.

`AskUserQuestion` 으로 객관식이 가능하면 그렇게 묻고, 아니면 목록으로 제시한다.

## Phase 4. 문서 확정

`docs/domain/` 에 저장한다.

```
docs/domain/
├── context-map.md                        # 컨텍스트 목록·분류·관계
└── <context>/
    ├── ubiquitous-language.md            # 용어표 (+ 상태 전이표)
    ├── aggregates.md                      # 애그리거트·불변식·리포지토리 초안
    └── events.md                          # 이벤트·페이로드·소비자
```

### 완성 기준

- [ ] 모든 컨텍스트가 Core / Supporting / Generic 으로 분류됨
      (Generic 은 **직접 만들지 않고 사서 쓴다**는 결론이 적혀 있어야 함)
- [ ] 컨텍스트 간 관계가 표로 있고, 통신 방식(Facade 호출 / 이벤트)이 정해짐
- [ ] 애그리거트마다 **불변식이 하나 이상** 적혀 있음 (없으면 애그리거트가 아니다)
- [ ] 상태값이 있는 개념은 **전이표**가 있음
- [ ] 용어표의 "아닌 것" 칸이 채워져 있음 (동음이의어 차단)
- [ ] **DDD 를 쓰지 않을 부분**이 명시됨 ("설정 관리는 단순 CRUD")
- [ ] 답을 못 정한 것은 `❓ 미결정` 으로 남아 있음 (추측으로 채우지 않음)

---

## Phase 5. 다음 단계 안내

문서를 확정한 뒤 사용자에게 알린다.

```
docs/domain/ 에 모델을 정리했습니다.
- 컨텍스트 N개, 애그리거트 M개
- 미결정 K건 (아래)

이제 구현할 기능을 정해 /ddd-plan 을 실행하면
이 문서의 용어와 경계를 기준으로 계획을 세웁니다.
```

이어서 `TASKS.md` 반영 여부를 묻는다.

---

## 하지 않는 것

- 코드 생성 (뼈대가 필요하면 `/ddd-scaffold`)
- 기술 스택·라이브러리 선택 (계획 단계의 일)
- 기획서에 근거 없는 개념 발명 — 이름이 없는 개념을 발견하면 **후보를 제시하고 사용자에게 고르게 한다**
- 전부에 애그리거트 만들기 — CRUD 인 곳은 CRUD 라고 쓴다
