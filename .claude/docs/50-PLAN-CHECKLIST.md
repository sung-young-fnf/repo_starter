# 구현 계획 체크리스트

**코드를 쓰기 전에** 통과해야 하는 목록이다. `/ddd-plan` 스킬과 `plan-reviewer` 에이전트가 이 문서를
기준으로 계획을 검증한다.

계획서에 이 항목들의 **답이 문장으로 적혀 있어야** 한다. "고려했다"가 아니라 "이렇게 한다"로 쓴다.

---

## A. 공통 — 계획서 필수 구성

- [ ] **어느 바운디드 컨텍스트의 일인가.** 기존 컨텍스트인가, 새로 만드는가?
      → 새로 만든다면 이유(언어가 다른가? 다른 팀/수명주기인가?)를 한 줄로.
- [ ] **유비쿼터스 언어**: 이번에 등장하는 새 용어를 `docs/domain/<context>/ubiquitous-language.md`
      에 추가할 목록으로 명시. 기획서에 없는 단어를 발명하지 않았는지 확인.
- [ ] **변경 파일 목록**을 레이어별로 나열 (domain / application / infrastructure / presentation).
      한 레이어만 바뀌는 계획은 대개 뭔가 빠진 것이다.
- [ ] **테스트 목록이 구현 목록보다 먼저** 나온다.
- [ ] **롤백 방법**: 마이그레이션이 있다면 되돌리는 방법.

---

## B. 도메인 설계

- [ ] 이 기능의 **애그리거트**는 무엇이고 경계는 어디까지인가?
- [ ] **한 트랜잭션에서 애그리거트 하나만** 수정하는가?
      → 둘 이상이면 → 도메인 이벤트 / 결과적 일관성으로 나눌 수 있는가? 못 나누면 그 이유를 적는다.
- [ ] 새 **불변식**이 있는가? 그 불변식은 애그리거트 안에서 지켜지는가?
- [ ] **VO 로 승격할 원시 타입**이 있는가? (문자열 ID, 금액, 기간, 상태값)
- [ ] **상태 전이**가 있다면 전이표를 계획서에 그렸는가? 허용되지 않는 전이는 무엇인가?
- [ ] 발행할 **도메인 이벤트**와 그 소비자는? 이벤트 이름이 과거형인가?
- [ ] 이 로직이 **엔티티/도메인 서비스에 들어가는가, UseCase 에 들어가는가?**
      → "여러 애그리거트가 필요한 순수 규칙"만 도메인 서비스. IO 가 섞이면 UseCase.
- [ ] **과설계 점검**: 사실상 CRUD 인데 애그리거트·이벤트를 만들고 있지 않은가?

---

## C. 백엔드 구조 (NestJS / Python 공통)

- [ ] **Facade 에 추가/변경되는 메서드 시그니처**를 적었는가? (Command → Result)
- [ ] 컨트롤러/라우터는 **Facade 만** 호출하는가?
- [ ] **트랜잭션 경계가 Facade 메서드 하나**인가? UseCase 안에 트랜잭션이 없는가?
- [ ] 새 **아웃바운드 포트**(알림·외부 API·스토리지)가 필요한가?
      → 인터페이스 위치(domain/repository vs application/port), DI 토큰, 구현체, **배선 지점**까지 명시
- [ ] **리포지토리 메서드 추가**가 필요한가? 그 메서드에 비즈니스 로직이 숨지 않는가?
      (`findAndApproveExpired()` 같은 이름이면 재설계)
- [ ] **ORM 스키마 변경**이 있는가? 매퍼도 함께 바뀌는가? 마이그레이션 파일이 계획에 있는가?
- [ ] 외부 시스템을 붙인다면 **ACL** 을 두는가?
- [ ] 다른 컨텍스트를 호출한다면 **그쪽 Facade** 를 통하는가? (테이블 직접 조회 금지)
- [ ] 에러: 새 도메인 예외와 **HTTP 상태 코드 매핑**을 적었는가?

---

## D. 프론트엔드 구조 (FSD)

- [ ] 이 변경은 **어느 레이어의 일인가** — `entities` / `features` / `widgets` / `views`?
      → 판단 근거 한 줄. (도메인 모델인가, 사용자 의도인가, 배치인가)
- [ ] 새 슬라이스가 필요한가? 이름이 규칙을 따르는가? (feature = **동사-명사**)
- [ ] 슬라이스의 **공개 API(`index.ts`)에 무엇을 내보내는가?** 내부 구현(mapper, dto)이 새지 않는가?
- [ ] **같은 레이어 슬라이스 간 의존**이 생기지 않는가? 생긴다면 공통을 어디로 내리는가?
- [ ] 서버 DTO → 도메인 모델 **매퍼 위치**는? (`entities/<name>/api/mapper.ts`)
- [ ] **타입·상태값 이름이 백엔드 유비쿼터스 언어와 같은가?**
- [ ] 서버/클라이언트 컴포넌트 경계: `'use client'` 를 어디에 붙이는가?
- [ ] 서버 상태인가 클라이언트 상태인가? **쿼리 키와 무효화 대상**을 적었는가?
- [ ] 로딩 / 빈 상태 / 에러 상태 UI 를 계획에 포함했는가?

---

## E. TDD

- [ ] **가장 먼저 쓸 실패 테스트**가 무엇인지 구체적으로 적혀 있는가?
- [ ] 계층별 테스트가 계획에 있는가?
      - 도메인 단위 (규칙·경계값·예외)
      - UseCase (Fake 리포지토리, 성공 + 실패 경로)
      - 통합 (실제 DB, HTTP 경유, DB 직접 조회 검증, 롤백 검증)
      - 프론트 (`model` 단위 + MSW feature 테스트 + 필요 시 e2e)
- [ ] **Fake 구현체**가 필요한가? 이미 있는가, 새로 만드는가?
- [ ] 시간·랜덤·ID 생성이 **주입 가능**한가?
- [ ] 통합 테스트의 **데이터 정리** 방식이 정해졌는가?

---

## F. 운영

- [ ] 로그에 **traceId / userId** 가 실리는가?
- [ ] 실패 시 어떻게 알아차리는가? (에러 로그 / 알림 / 메트릭)
- [ ] 성능: N+1 쿼리 가능성, 인덱스, 목록 API 의 페이지네이션
- [ ] 권한: 이 오퍼레이션을 누가 호출할 수 있는가? 검사 지점은 어디인가?
- [ ] 동시성: 같은 애그리거트에 동시 요청이 오면? (낙관적 락 / 유니크 제약)
- [ ] API 스펙 문서와 `.http` 파일 갱신이 계획에 있는가?

## 계획을 반려하는 신호

`plan-reviewer` 는 다음 중 하나라도 보이면 **REJECT** 한다.

1. 컨트롤러가 UseCase/리포지토리를 직접 호출하는 계획
2. 트랜잭션이 UseCase 안에 있거나, 한 트랜잭션에서 애그리거트 2개 이상 수정 (근거 없이)
3. ORM 엔티티를 도메인 엔티티로 겸용
4. 테스트 계획이 구현 뒤에 오거나, "구현 후 테스트 추가" 로 적힘
5. 도메인 규칙이 UseCase / 컨트롤러 / React 컴포넌트에 들어가는 계획
6. 프론트 계층 판단 없이 "컴포넌트 만들고 API 붙임" 수준의 계획
7. 새 포트를 만들면서 **배선 지점**이 빠짐
8. 다른 컨텍스트의 테이블/리포지토리 직접 접근
9. 유비쿼터스 언어에 없는 새 용어를 정의 없이 도입
10. 사실상 CRUD 인데 DDD 풀세트를 적용하는 과설계 (반대 방향의 반려)
